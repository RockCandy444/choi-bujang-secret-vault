# 11단계 접속 화면과 승인 연결 상태

현재는 **운영 기기 승인·등록 상태·요청 서명 검증 계약이 제공되지 않은 저장점**입니다.
공식 시작 틀의 `DECIDER_REQUEST.md`는 엔진의 `deviceRegistered`만 정의하며,
학생 서버가 그 값의 출처를 검증하거나 기기를 등록하는 API는 정의하지 않습니다.
2026-10-14 공식 공개 시작 틀과 제작자의 공개 표본을 조회했습니다.
표본의 `api/device/status.js`도 실제 등록 세션 없이 `approved:false`만 반환합니다.
학생은 운영 계약 문서가 없다고 확인했습니다. 표본의 가상 상태를 운영 승인 근거로 복사하지 않습니다.

## 현재 구현

- `GET /api/device/status`: 503 `{approved:false,error:"DEVICE_APPROVAL_NOT_CONFIGURED"}`.
- 같은 출처의 `POST /api/device/request`: 같은 503. 접수 번호·대기 등록·승인 권한을 만들거나 저장하지 않습니다.
- 승인 요청의 다른 출처·누락된 Origin은 403, 잘못된 메서드는 405입니다.
- 두 경로는 `no-store`입니다. 기기 키·토큰·본문·요청 신원을 저장하거나 로그에 출력하지 않습니다.
- 로그인 뒤 화면이 상태를 확인합니다. 미승인·미준비·오류·잘못된 응답이면 메모 목록을 요청하지 않고 편집기도 숨깁니다.
- 요청 버튼의 응답만으로 자료실을 열지 않습니다. 접수 응답 이후 별도의 서버 상태 확인이 필요합니다.
- 상태 재확인·세션 갱신·로그아웃 때 자료와 편집 값을 지우며, 늦은 이전 응답은 자료실을 다시 열지 못합니다.

화면의 정상 경로는 시험에서 주입한 `200 {approved:true,reason:...}` 응답으로만 검사합니다.
현재 서버는 이 응답을 발급할 수 없습니다. 이 화면 응답 형식은 운영 엔진 계약을 뜻하지 않습니다.
실제 연결 전에는 보호 자료를 표시할 수 없는 준비 상태입니다.

## 운영 연결에 필요한 확인

운영 측이 승인 요청 API, 등록 세션 증명과 검증 절차, 사용자·기기·프로젝트 연결,
만료·회수, 재확인, 요청의 메서드·경로·본문 서명 검증 계약을 제공해야 합니다.
그 계약으로 서버를 연결한 뒤 승인된 기기의 정상 화면·CRUD와 미승인 접근,
서명 없음·서명 뒤 경로 변경·본문 변경을 실제로 검사합니다.
브라우저 헤더·버튼·설치 상태·로그인만으로 승인하지 않으며 요청 계약에 임의 필드를 추가하지 않습니다.

기존 메모 API의 로그인·소유자 보호와 판정기의 여섯 규칙은 유지했습니다.
화면에서 자료를 숨기는 기능만으로 직접 API의 기기·서명 검증이 연결됐다고 주장하지 않습니다.
기기 제어 두 경로를 메모 릴레이 허용 경로에 추가하지 않았습니다.

검사: `node --test test/step11.test.mjs test/notes.test.mjs`.
모의 승인 응답의 정상 경로와 미승인·형식 오류·늦은 응답 거부를 검사하며,
실제 등록 기기 성공이나 운영 심판 판정의 증거가 아닙니다.
