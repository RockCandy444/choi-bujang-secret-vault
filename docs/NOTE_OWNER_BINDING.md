# 판정기 소유권 연결 작업 시작 (2026-10-13)

## 현재 확인 결과

기존 판정기에 같은 가상 메모 경로와 서로 다른 A/B 가명 주체를 넣으면
두 요청 모두 `allow`입니다. 이 결과를 이번에 직접 확인했습니다. 자료 API는
별도로 검증된 로그인 사용자와 DB의 소유자를 비교해 상대 접근을 거부하지만,
판정기 자체의 소유권 구분은 아직 연결되지 않았습니다.

## 이번에 추가한 검사 기반

`src/verify-note-owner.mjs`의 `createNoteOwnerVerifier`는 서버 코드에서만
사용하는 검사 생성 함수입니다. 요청에 권한 필드를 추가하지 않습니다.

- `resolveSubject`: 운영 측이 검증한 주체 연결 저장소를 읽는 서버 함수.
  반·프로젝트·가명 주체가 모두 같은 연결에서 Auth 사용자 UUID를 얻어야 합니다.
- `readNoteOwner`: 같은 반·프로젝트의 메모 저장소에서 UUID로 행의 ID와
  저장된 `owner_id`를 읽는 서버 함수.

두 출처가 확인되고 선택한 메모 UUID 및 소유자가 일치할 때만 `true`를
반환합니다. 출처 함수 없음, 연결 누락, 반·프로젝트·주체 불일치, 소유자
누락, 다른 메모·소유자, 조회 오류는 모두 `false`입니다. 허용을 캐시하지
않으며 본문·역할·사용자 번호를 요청에서 받아 권한으로 사용하지 않습니다.
조회 예외와 개인 식별값도 출력하지 않습니다.

## 실제 연결에 필요한 것

현재 공식 `docs/DECIDER_REQUEST.md`에는 `subjectId`를 Supabase 사용자 UUID에
연결하는 공식 서버 조회 인터페이스가 없습니다. 따라서 이 변경은
**검사 기반과 가상 A/B 검사만 추가한 상태**입니다. 운영 저장소나 주체 연결
자료를 만들어 넣지 않았으며 `src/decider.mjs`에는 아직 연결하지 않았습니다.
엔진·API·로그인·기기·추가 확인·기존 정상 요청은 변경하지 않았습니다.

실제 연결을 위해 운영 측에 확인할 항목은 다음과 같습니다.

> `classId`, `projectId`, `subjectId`에 대응하는 검증된 Auth 사용자 UUID를
> 서버에서 조회할 수 있는 공식 인터페이스와, 그 인터페이스가 판정기 실행
> 환경에서 제공되는 방법을 알려 주세요. 사용자 번호·토큰을 채팅에 보내는
> 방식이 아닌 서버 연동 계약이 필요합니다.

이 연결 없이 가명 주체를 `owner_id`와 직접 비교하거나 A의 실제 사용자
번호를 코드에 고정하지 않습니다. 조회 함수를 브라우저 요청이나 헤더에서
등록할 수도 없습니다. 연결 뒤에도 자료 API의 DB 소유자 조건과 반환 소유자
재확인을 유지해야 합니다. 판정기 조회 이후 소유자가 바뀌는 경우를 API가
다시 막아야 하기 때문입니다.

## 확인 방법

실행: `node --test test/note-owner.test.mjs`.
파일 탐색기 **test → note-owner.test.mjs**를 열어 터미널 결과와 대조합니다.
정상은 서버 출처를 모의한 A의 자기 메모 검사 `true`, 거부는 B의 A 메모
검사와 연결·소유자·출처 누락의 `false`입니다. 모의 자료는 메모리에서만
만들며 실제 학습 DB나 운영 엔진을 수정하지 않습니다.

이 검사는 실제 `decide(request)`의 A 허용·B 거부나 심판 판정의 증거가
아닙니다. 실제 소유권 연결과 운영 검사는 미완료입니다.
